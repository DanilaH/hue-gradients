# Подготовка каталога ежедневных задач

[Банк «Полусна»](spec/candidates/levels-0.1.json) содержит 30 собственных кандидатов. Даты назначаются после игрового просмотра относительно реального запуска. Каталог и тестовый пример ниже готовятся локально.

1. `python3 tools/stage-daily.py review` выводит SHA-256 банка, версию правил, отпечаток и математический минимум каждой задачи. Проверка пересчитывает RGB, допустимость опор и старта независимо от генератора. Игровой просмотр включает различимость соседних цветов и прохождение на устройстве. [Листы задач](spec/candidates/README.md)
2. Для проверенных задач составить `reviewed-plan.json`. Скопировать `bankSha256` и `rulesVersion` из отчёта. В `slots` записать `date` (UTC `YYYY-MM-DD`), `candidateId` и точный `fingerprint` каждой задачи. Для карточки события в книгах указать `feature` с полями `id` и `title`. План с запасом будущих задач остаётся у редакции.
3. `python3 tools/stage-daily.py stage --plan reviewed-plan.json --through YYYY-MM-DD --out .test-output/daily-staged` собирает новый снимок. Для обновления передать `--previous` с текущим опубликованным снимком. Инструмент проверяет старые хеши и отклоняет подмену или исчезновение существующего дня и откат даты. Дата `--through` передаётся явно.

В снимке `catalog.json` содержит контрольные суммы месячных манифестов из `months/`. Каждая запись месяца указывает SHA-256 JSON уровня из `levels/`. Будущих дат и их файлов в выходном каталоге нет. Статистика команды отдельно показывает запас. Порог выпуска из дорожной карты — 30 принятых задач с запасом не менее 14 после старта. [M6](spec/ROADMAP_1_0.md#m6--daily-как-поддерживаемый-сервис)

Публикации нужен провайдер с доверенным временем. Он загружает и перепроверяет подготовленные файлы, затем атомарно переключает указатель на весь снимок. Провайдер передаёт в [проверку снимка](../src/app/dailyCatalog.ts) независимо подтверждённые SHA-256 файла `catalog.json` и UTC-время. Проверка читает исходные байты, сверяет месяц, задачу и отпечаток поля и выдаёт одну `DailyFeed` для `dailySource` только после проверки всего снимка. Версией становится SHA-256 каталога. Дата публикации из файла не определяет текущий день. Повреждённый ответ оставляет ранее принятый кеш в игре.

Обычное обновление сохраняет прежние слоты. Отзыв ошибочной задачи и переход на новую ревизию остаются отдельными сценариями живого сервиса.

Проверка команды — `python3 tests/stage_daily_test.py -v`. Игровой маршрут на двух подготовленных снимках — `node tools/daily-browser-check.mjs PATH_BEFORE PATH_AFTER`. Для него нужны два последовательных дня с задачей на текущий день в каждом снимке. Браузерный тест подставляет UTC-полночь, получает исходные файлы, сравнивает старт у двух профилей, отклоняет повреждённое обновление, затем принимает исправное и повторяет старый день офлайн.

Необязательный третий путь в этой команде указывает на тестовый снимок всех 30 кандидатов. Прогон загружает его один раз, отключает источник и решает каждое поле через касания в Chromium. Для плана прогона можно взять все отпечатки из `review`, назначить последовательные тестовые UTC-даты с 31 января 2026 и собрать снимок по 1 марта включительно. Игровой просмотр различимости оттенков и темпа проходит отдельно.

Для снимка с карточкой события запустить `node tools/books-browser-check.mjs PATH_WITH_EVENT`. Проверка открывает событие из книг в отключённой сети, дважды проходит поле и проверяет, что сохранилась одна отметка за дату.

## Очередность для игрового просмотра

В исходном порядке каждая десятка повторяет размеры, маски опор и минимумы предыдущей. Черновой порядок убирает три случая, когда соседние задачи одного размера и сохраняет все десять типов раскладки в каждом блоке. Номера соответствуют суффиксам `gradient-daily-NNN` и пока не привязаны к датам.

| Позиции | Номера кандидатов |
|---|---|
| 1–10 | 001, 002, 003, 004, 006, 005, 008, 007, 009, 010 |
| 11–20 | 012, 011, 015, 020, 014, 016, 013, 017, 018, 019 |
| 21–30 | 021, 024, 028, 022, 026, 027, 023, 025, 029, 030 |

Начать проверку различимости цветов с 027, 016 и 010. У них три наименьших расстояния между подвижными цветами в банке по Oklab. У 027 также максимум в 10 обменов по математическому минимуму. [Расчёты по банку](spec/candidates/validation-0.1.json)
