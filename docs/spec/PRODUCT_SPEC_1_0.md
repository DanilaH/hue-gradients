# ХУЕ / «Полусон» — техническое задание 1.0

**18 ноября 2026 · рабочий baseline для разработки полного первого релиза.**

Это обязательный продуктовый контракт, а не отчёт о готовой игре. «Полусон» — рабочее художественное название; имя для магазинов утверждается отдельно. Сейчас заказана подготовка документов: приложение, фон и опубликованная проба в этом проходе не изменяются.

## 1. Назначение и порядок применения

Игрок меняет местами цветные плитки и собирает цельный градиент. Повторяемый цикл: выбрать задачу → рассмотреть опоры → восстановить цвет → получить выразительный результат и работу в альбоме → продолжить кампанию, daily или собственную композицию. Удовольствие должно приходить от сравнения оттенков, прямого отклика и появления цельной картины; мета поддерживает этот цикл.

Первым читать этот документ, затем [роудмапу](ROADMAP_1_0.md) и [матрицу приёмки](ACCEPTANCE_MATRIX_1_0.md). Точные специальные контракты перечислены в §17 и входят в ТЗ по ссылке. В передаваемом архиве они приложены вместе с банком данных и исходным визуальным референсом.

Приоритет: последнее явное решение владельца → этот baseline и его журнал изменений → специальные контракты → исторические исследования. Если специальный документ уточняет область, не противореча baseline, его подробности обязательны. Спорное правило нельзя молча выбрать по старой дате или удобству реализации: фиксировать расхождение и его разрешение.

**OWNER** — прямое решение владельца. **BASELINE** — конкретный рабочий выбор для реализации, допускающий последующую проверяемую корректировку. **GATE** — внешняя зависимость или приёмка, которую пока нельзя объявить закрытой. Слово BASELINE не означает разрешение пропустить функцию.

| Статус | Зафиксированное решение |
| --- | --- |
| OWNER | Цветовая головоломка; большое поле, blurry/dreamy/PSX настроение; живой фон от игрока и цветов |
| OWNER | Образец оформления — прикреплённый концепт с цветовой дымкой, свечением и призмой; сейчас зафиксировать его в ТЗ |
| OWNER | Прежний шрифт не понравился; новый шрифт ещё не утверждён. Ссылка на картинку не отменяет эту претензию |
| OWNER | Daily, редактор, облако и мета для удержания обязательны в первом релизе; рабочий план без энергии |
| BASELINE | Четыре главы по 15 задач; открытие следующей после 10; 30 принятых daily перед выпуском |
| BASELINE | Альбом, личное мастерство, шесть макетов экспорта; бесплатная помощь; баннер и редкий interstitial |
| BASELINE | Общее TypeScript-ядро; Android/RuStore и Яндекс Игры как первые адаптеры; API/PostgreSQL |
| GATE | Телефонная и художественная приёмка, identity/SDK capabilities, инфраструктура, реальные публикационные конфигурации |

Не включать автоматически: энергию, жизни, ожидание восстановления, валюту, IAP/rewarded, ежедневную обязательную серию, рейтинги, сезоны, public UGC, социальную ленту, импорт чужих работ, сюжетную кампанию, маскота, управление 3D-миром. Дополнительные платформы проверяются отдельными адаптерами; низкий трафик сам по себе не причина исключения доступной площадки.

## 3. Правила поля и попытки

**CORE-01. Данные.** Позиции row-major с нуля; tileId равен позиции в решении. Snapshot содержит width/height, точные solvedTileColors, pinnedPositions и startTileAtPosition. Старт официальной задачи фиксирован. Повтор возвращает его, а не новый shuffle. Победа — точное совпадение всех ID с решением; цветовой допуск не используется.

**CORE-02. Обмен.** Разрешён обмен любых двух разных подвижных плиток, включая уже правильно стоящие. Pin нельзя выбрать или переместить. Один принятый обмен даёт один ход; выбор, отмена, нажатие pin, отпуск на исходную клетку или за полем не дают ходов. Таймера, лимита ходов и поражения в обычной кампании/daily нет.

**CORE-03. Tap–tap.** Первый tap выбирает. Второй по другой подвижной меняет плитки. Повтор по выбранной, пустое место или pin снимают выбор. Pin при первом знакомстве объясняется коротким текстом; далее только локальный отклик. Подсказка не делает обмен вместо игрока.

**CORE-04. Drag.** Один pointer, порог 8 CSS px как начальная настройка. Захват сохраняет точку касания внутри плитки; визуальная плитка непосредственно следует пальцу. Drop определяется последними координатами pointerup и канонической сеткой, даже если pointermove ещё не отрисован. Pin/вне поля/исходная клетка отменяют. Второй палец игнорируется. Pointercancel, потеря capture, фон, resize с изменением геометрии или смена экрана отменяют жест; поздний callback не совершает ход.

**CORE-05. Операция и отклик.** Press виден сразу. Принятие обмена, счётчик, snapshot и operation ledger сохраняются атомарно. До подтверждения этой записи следующий изменяющий save ввод ждёт видимого pending-состояния; сеть не участвует в локальном подтверждении. Ошибка возвращает последнюю подтверждённую модель. Косметическая посадка не блокирует следующий ход: при новом жесте завершается в канонические позиции. Начальный settle — 150 ms, настраиваемый; очереди старых жестов нет.

**CORE-06. Помощь.** Бесплатное явное действие показывает готовое поле до закрытия игроком. До раскрытия записать assisted и assistsUsed. Preview не меняет ходы/перестановку и не делает обмен. Повторное нажатие при открытом preview не расходует ещё одну помощь. Back, закрытие и уход в фон возвращают исходную партию. Assist сохраняется при продолжении; новое прохождение начинается с новой попытки. Кнопка «Посмотреть финал» из визуальной пробы — инструмент демонстрации, в релизное меню незавершённой партии не переносится: показ решения проходит только через эту помощь.

**CORE-07. Результат.** Последний обмен одной транзакцией сохраняет решение, completion, нужный best, права и outbox. После commit запускаются результат и звук. При повторном запуске результат уже завершённой попытки восстанавливается без повторной награды. Кнопки «Дальше», «В альбом», «Повторить» доступны без обязательного ожидания церемонии; переход вперёд — отдельное действие.

**CORE-08. Минимум и рекорды.** Для перестановки подвижных ID минимум обменов = число подвижных − число циклов, включая циклы длины 1. Это математический минимум, не «среднее мира» и не оценка времени/трудности. Показывать его в результате и информации о задаче; постоянный HUD не обязан содержать все вторичные числа. Best хранить раздельно с помощью/без помощи по fingerprint + rulesVersion. Новая более быстрая assisted-попытка не заменяет clean best.

**CORE-09. Жизненный цикл.** После обычного выхода, background, убийства процесса и force-stop возвращается последняя подтверждённая запись. Pointer/выбор/анимация/открытый help не восстанавливаются. Back закрывает верхний слой; затем возвращает к предыдущему экрану с сохранением. Рестарт требует подтверждения и сбрасывает только текущую попытку, сохраняя completion/best/права.

**CORE-10. Обучение.** Первый экран даёт действие «Поменяй две плитки местами», без экскурсии по всем функциям. firstSwapDone записывается с обменом; pinExplained и onboardingVersion сохраняются отдельно. Повторный запуск/повтор уровня не запускает обучение заново. Правила доступны вручную.

## 4. Кампания и выпуск контента

**CONTENT-01.** Официальный стартовый банк — gradient-001…060, четыре главы по 15. Существующие первые 15 сохраняют ID, цвета, pins и start. Если человеческая проверка потребует изменения, выпускать новую содержательную revision с явной совместимостью; не переписывать старые определения и сейвы по порядковому номеру.

**CONTENT-02.** №1 открыт сразу; №2–5 открываются последовательно. После №5 доступны №6–15. В следующей открытой главе доступны все 15. Рекомендуется наименьший непройденный номер выбранной главы; игрок может выбрать другую доступную задачу. Следующая существующая глава открывается после 10 уникальных завершений предыдущей; при 15/15 — отметка полной страницы. Повторы, daily и собственные работы не увеличивают прогресс кампании. Помощь обычное завершение не отменяет.

| Глава | Задачи | Задача дизайна |
| --- | --- | --- |
| 1 | 001–015 | Понять обмен, опоры, направления; переносить освоенное действие |
| 2 | 016–030 | Сравнивать верх/низ и боковые края, переходить от рамки к углам |
| 3 | 031–045 | Использовать внутренние опоры и согласовывать несколько направлений |
| 4 | 046–060 | Чередовать освоенные комбинации и более открытые поля |

**CONTENT-03.** Проверять роли practice/combine/recovery на людях. Размер, минимум и новый оттенок не считаются самостоятельным доказательством сложности или разнообразия. Короткие передышки в кандидатах глав 2–4 находятся на позициях 5/8/13; их статус подтверждается прохождением, не названием.

**CONTENT-04.** Для допуска каждого официального snapshot: структурный validator → законный witness → точное изображение старт/решение → просмотр на целевых дисплеях → человеческое прохождение → редакционный статус accepted/revise/reject с причиной. Четыре уже найденных цветовых предупреждения должны получить отдельные решения. Автоматический PASS не заменяет этого этапа.

**CONTENT-05.** 30 daily-кандидатов gradient-daily-001…030 пока UNASSIGNED. Перед релизом нужны 30 принятых задач; даты назначаются publisher-процессом. Далее поддерживать не меньше 14 принятых задач запаса, пополняя пачками по семь. Владелец процесса и порядок действий при исчерпании обязательны до запуска daily.

## 5. Мета, альбом и награды

**META-01.** Один альбом: «Кампания», «Ежедневные», «Мои работы». Базовая карточка даётся один раз по logical levelId/slotId. Повтор обновляет метаданные/best, не создаёт новую награду. Не показывать готовые решения незавершённых задач в пустых местах альбома.

**META-02.** С первой победы доступны просмотр результата, чистый экспорт и создание своей версии. Пустой редактор доступен сразу независимо от прогресса. Доступность, помощь, звук и движение не закрываются наградами.

| Право / отметка | Условие | Результат |
| --- | --- | --- |
| Следующая глава | 10 разных завершений предыдущей | Открывается существующая опубликованная глава |
| Полная страница | 15/15 в главе | Отметка и экспорт страницы 3×5 |
| export-caption | 5 разных campaign | Одна работа с подписью |
| export-strip | 15 разных campaign | Лента из трёх разных работ |
| export-grid | 30 разных campaign | Сетка из четырёх разных работ |
| export-frame | 3 разных daily-slot | Работа с декоративным полем |
| export-diptych | 7 разных daily-slot | Две разные работы |
| export-postcard | 14 разных daily-slot | Работа с областью личной подписи |
| Без помощи | Чистая победа этой попытки | Личная отметка, отдельный clean best |
| Идеально без помощи | Чистая победа за математический минимум | Отдельная необязательная отметка мастерства |

**META-03.** Архивные daily учитываются в 3/7/14. Семь задач за вечер — семь задач, не семь дней возвращения. Непрерывной серии, обнуления за пропуск и «возврата серии» за оплату нет.

**META-04.** Несколько наград сохраняются вместе; UI показывает один итог и доступный список, без очереди обязательных окон/«Забрать». После sync права появляются без повторной церемонии. Изменение policyVersion не отбирает earned-права и уже открытые главы. После шести форматов нет фиктивного седьмого; дальнейшие цели — полные главы, новые daily, свои композиции и мастерство.

## 6. Daily и архив

**DAILY-01.** Один общий slotId = UTC YYYY-MM-DD с опубликованной content revision и фиксированным стартом. Архив сохраняет ту же идентичность. Обновление в 00:00 UTC; UI показывает локальное время обновления по зоне устройства. Для Екатеринбурга это 05:00, но значение не зашивается глобально. Часы и смена зоны не открывают будущие задачи.

**DAILY-02.** Получение каталога не требует входа. Новый незагруженный слот требует сети и доверенного опубликованного manifest; кешированные задачи и начатые партии работают offline. При устаревшем времени каталога показывать последнюю подтверждённую дату. Кампания и редактор не ждут daily endpoint.

**DAILY-03.** Переход суток не прерывает партию. Завершение относится к исходному slotId; текущий новый слот доступен независимо. Пропущенные опубликованные задачи можно решить позже в любом порядке. Нет дедлайна, обязательного таймера или потери заработанного.

**DAILY-04.** Скачивать и проверять bytes/hash/schema/content identity до атомарной установки ref+blob. Повреждённый ответ не уничтожает пригодный кеш. Отозванный уровень не подменять внутри партии: предложить новую попытку, сохранив старую для восстановления; completion и earned-права не отнять. Best несопоставимых revision не смешивать.

**DAILY-05.** При отсутствии публикации: понятное сообщение и архив. Не генерировать непроверенный уровень на клиенте и не выдавать старый слот за новый. Publisher сначала загружает immutable blobs и проверяет их, затем атомарно публикует catalog/slots. Будущие байты не выдаются публичным календарём.

## 7. Редактор и собственные работы

**EDITOR-01.** Пустой draft: 4×4, угловые pins, собственная палитра, «Моя композиция». Копия решённой работы получает новый draftId/provenance; исходник, completion и рекорд не меняются. Размер: width 1…6, height 1…5, максимум 30; минимум две подвижные и две разные по цвету опоры. 1×1/1×2/1×3 не могут стать playable.

**EDITOR-02.** Четыре sRGB #RRGGBB угла; для одной оси два конца, неиспользуемые углы нормализуются. Плитки строятся билинейно в sRGB byte-каналах с округлением половины вверх, row-major. Не заменять интерполяцию на другую «красивую» модель без новой content/rules revision.

**EDITOR-03.** Инструменты «Размер / Палитра / Опоры / Старт» имеют явный режим. Опоры переключаются tap, без игрового обмена. Цвет/размер показывают preview; «Готово/Применить» — одна правка, «Отмена» — никакой. Resize сбрасывает pin-маску к углам/концам с сохранением предыдущей revision. Ползунок не порождает десятки версий.

**EDITOR-04.** «Другой старт» создаёт один цикл по подвижным ID; сохраняются seed и полная перестановка. Replay неизменной работы возвращает тот же старт. Имя: plain text, trim, пустое → «Моя композиция», максимум 80 Unicode code points. Имя/дата/seed при неизменном стартовом поле не меняют gameplay fingerprint.

**EDITOR-05.** Валидатор различает hard errors и предупреждение. Блокируют игру: некорректные размеры/индексы/цвета/реконструкция/перестановка, сдвинутый pin, недостаток опор/подвижных, точные одинаковые RGB среди подвижных, старт уже решён, неоднозначность цели при сохраняющих опоры симметриях. CLOSE_COLORS_REVIEW при Oklab <0.025 — предупреждение, не универсальный порог зрения; личную проверку можно запустить. Невалидный draft можно сохранить, но нельзя играть.

**EDITOR-06.** Fingerprint = SHA-256 canonical JSON от width, height, normalized RGB, startTileAtPosition, sorted pins; rulesVersion учитывается отдельно. Перед проверкой игрой сохраняется неизменный snapshot. Состояния: «Черновик с ошибками» → «Можно проверить игрой» → «Пройдена автором». Последнее требует победы соответствующей revision; помощь разрешена и помечена. Это не сертификат интересности/доступности.

**EDITOR-07.** Содержательная правка даёт новую revision и снимает её авторское прохождение; rename — нет. Одна работа с историей остаётся одной карточкой. Собственные победы не фармят campaign/daily и экспортные пороги. Для составных макетов разные revision одной работы не считаются разными работами.

**EDITOR-08.** Завершённые правки записываются атомарно до «Сохранено». Имя может иметь debounce 300 ms, но Back/запуск/уход сначала завершают запись. Ошибка сохраняет форму с Retry; уход с несохранёнными правками предлагает остаться либо явно выйти без них. Dirty-состояние не объявляется сохранённым. Локальные черновики и версии синхронизируются, конфликтующие ветки остаются восстановимыми.

## 8. Художественная постановка и динамический фон

**ART-01. Основной референс.** [Прикреплённый владельцем концепт](https://chatgpt.com/library?file_id=libfile_fde3_f-4518cf7dfd948191a0330e42934c5d7a_2841ca9da26c8191b7a266fa9b41a810&account_id=personal), 1774×887. Это статичный сгенерированный концепт двух состояний, не скриншот приложения; по нему не заявляются измеренные motion/тайминги.

Требуется воспроизвести его характер: крупные светящиеся облака персикового, мятно-бирюзового, розового, сиреневого и синего; глубокие сливовые края; мягкая дымка, деликатное зерно и оптическое свечение. Цвет заполняет весь экран. Сама палитра меняется с задачей: изображение задаёт свет/материал/контраст, а не пять навсегда зашитых цветов.

**ART-02. Иерархия.** Поле — главный объект, без маленькой карточки на «странице приложения». HUD короткий и лёгкий. На победе допустима одна парящая полупрозрачная низкополигональная призма со свечением. Она декоративна, не валюта, ресурс или новая коллекция. В меню и альбоме сохраняется атмосфера, а контент и подписи остаются читаемыми; не превращать их в набор гостиничных карточек с декоративными KPI.

**ART-03. Шрифт.** Псевдопиксельный/объёмный шрифт картинки не принят. Golos Text из браузерной пробы — кандидат, не финальное решение. На этапе художественного среза сравнить максимум два реальных лицензированных шрифта на одинаковых русских экранах: HUD, «Собрано», длинное название работы, настройки 150%. Зафиксировать итоговую гарнитуру, начертания, цифры, размеры и роли. Не генерировать надписи как bitmap, не добавлять тяжёлую экструзию.

**ART-04. Слои.** Размытый ambient → мягкая виньетка/зерно → точная непрозрачная сетка → отдельные pin/selection/drag → читабельный UI. Grain/bloom/chromatic effects не перекрашивают сравниваемые площади активных плиток. Сгенерированные тени внутри клеток референса не являются разрешением исказить данные. Pin — контрастная точка с двухцветной границей; выбор — светлые угловые скобки/контур, без индикатора правильности. Никакого PSX-дрожания hitbox или квантизации близких RGB.

**ART-05. Источник фона.** Учесть текущее расположение RGB, а не только среднее/гистограмму: при swap набор цветов одинаков. Пространственные пробы и реакция на указатель могут переиспользовать идею пробы, но её 3×3 samples, blur 34 px и малоконтрастный вид не закрепляются как художественный стандарт. Сравнить собственный renderer с референсом по свету, насыщенности, глубине и мягкости; не объявлять готовым только потому, что градиент анимируется.

**ART-06. Честность подсказок.** До победы/явной помощи фон не использует скрытую корректность, число верных клеток, оставшийся минимум или расстояние до решения. **ART-07. Победа.** Сразу после надёжного сохранения читаются итог и действия. Собранное поле остаётся воспринимаемым в переходе, затем может раствориться в полноэкранном градиенте как на правой половине концепта; «Посмотреть поле» возвращает его. Старое требование постоянно держать отдельную панель исключительно за пределами сетки заменяется этим двухфазным состоянием. Ни сохранение, ни next/album не зависят от окончания tween.

**ART-08. Настройки и качество.** Отдельно «Движение фона»/уменьшение движения, звук эффектов, haptics где доступны. Уважать системное reduced motion. При ограниченном GPU уменьшать частоту/разрешение ambient, число декоративных слоёв и эффект призмы, сохраняя точный цвет поля и прямой ввод. Профиль качества выбирается по измерению; 30 FPS фоновой пробы не доказывает скорость итогового приложения.

**ART-09. Звук.** Минимальный обязательный набор: короткий собственный звук принятого обмена и более выразительный звук победы; haptic на те же события, если включён. Cancel/no-op не звучат как успех. Музыка не обязательна для приёмки первой версии; это отдельная необязательная художественная добавка без роста механик.

Страница главы 1800×3000, 3×5 — отдельное системное представление, не седьмой unlock. Поле вписывается целиком, не обрезается и не растягивается; фон/рамка располагаются снаружи.

**EXPORT-03.** Caption до 80 code points/двух строк, postcard до 140/четырёх. Реальный renderer измеряет текст; не обрезать молча и не уменьшать бесконечно. Для макета нужны разные завершённые работы; недостаток объясняется. Отмена share сохраняет preview/право, ошибка записи ОС не откатывает победу. Share sheet вызывается только действием игрока; его открытие не считается подтверждённой публикацией в другом приложении.

## 11. Архитектура, сохранения и облако

**TECH-01. Границы.** Доменное TypeScript-ядро независимо от Phaser/DOM/SDK. Отдельно renderer/input, local store, sync client, content/catalog, платформенные lifecycle/ads/auth/share. Один небольшой HTTPS API и PostgreSQL, без универсальной backend-платформы и брокера. Браузерная художественная проба не служит каркасом хранения и всего релиза.

**TECH-02. Bootstrap.** Перед consumer init прочитать актуальные AGENTS/Task Router/API; выбрать проверенный kit commit и раздельно записать runtime/guidance pins. Ранее проверенная база — 4e826ff378dfd2f4705a31a894400ae6268ca6f9; это исторический кандидат, не приказ игнорировать новые исправления. Для Yandex использовать tested bootstrap. Для Android полноценного tested kit bootstrap пока нет: отдельный Capacitor/native scaffold и приёмка SQLite/lifecycle/ads обязательны. Не копировать Android Mobile Ads в web.

**TECH-03. Local.** Android — SQLite через ограниченный bridge, web — IndexedDB. Commit включает snapshot, доменные последствия, operationId/result и outbox в одной транзакции. Один writer на профиль; web tabs используют transactional CAS localRevision. LocalStorage из пробы не заменяет эти гарантии. Optional cloud/analytics/ads не стоят на пути локального старта и принятия хода.

**TECH-04. Recovery.** OperationId создаётся до записи. При неизвестном результате читать ledger: применена → вернуть подтверждённое; отсутствует → повторить тот же ID; недоступно → recovery UI. Не принимать старый snapshot под новым revision. На загрузке проверять schema/content/rules, биекцию/pins/счётчики. Повреждение одной партии не обнуляет весь профиль. Миграция: backup → validate → migrate → validate → commit.

**CLOUD-01. Сущности.** Profile/epoch, installationId, operation ledger, logical completions, best по fingerprint/rules/category, attempt и work revision graph, earned rights, outbox фиксированного адресата, immutable content и UTC slots. Точные ключи и API — TECHNICAL_SPEC §§4–10. Новая schema не сбрасывает отсутствующие в старой schema поля в defaults.

**CLOUD-02. Identity.** Вход добровольный. Android — проверенный Яндекс ID flow с PKCE/state без секретов в клиенте; backend проверяет proof. Yandex Games — platform SDK и проверенный signed Player proof, не голый playerId. Namespace двух платформ раздельный; совпадение имени/email не объединяет профили. Восстановление между устройствами внутри подтверждённого профиля обязательно; cross-platform linking не заявляется готовым.

**CLOUD-03. Внешний блокер.** Доступность ключа signed Player для данной игры проверить в M0 на реальном draft/кабинете. Официальная документация связывает ключ с подключением инап; отсутствие ключа нельзя обходить доверием клиентскому UID. IAP не добавляется в продукт автоматически. При недоступности capability нужен отдельный проверенный identity-вариант и корректировка контракта до принятия web cloud.

**CLOUD-04. Sync.** Изменяющий batch атомарен, operationId/payload неизменны, owner извлекается из сессии; epoch проверяется под DB lock вместе с записью. Потерянный ответ допускает повтор тех же ID. Неверный ресурс/cursor/parent другого профиля не раскрывает данные. Best/completion/права сливаются по семантике, а не целым файлом save. Конкретные ошибки, retry/лимиты — TECHNICAL_SPEC §7.

**CLOUD-05. Конфликт.** Продолжение потомка заменяет предка. Две расходящиеся ветки сохраняются обе; пользователь выбирает текущую, создаётся resolution node. Не смешивать клетки и не выбирать победителя по часам/числу ходов. Assisted монотонен внутри попытки; clean best относится только к соответствующей завершённой ветке. Нерасходуемые права объединяются без повторного начисления.

**CLOUD-06. Гость/аккаунты.** Перенос фиксирует transferId, источник и адресата; chunk повторяется безопасно. Не удалять guest до подтверждённого receipt и локального commit. Account A → guest → B не копирует данные A. Logout прекращает доступ к vault и токенам, но не перенаправляет его outbox новому пользователю. Поздние callbacks изолированы sessionGeneration.

**CLOUD-07. Reset/delete.** Online recent-auth reset увеличивает epoch, очищает campaign/daily/earned/attempts, сохраняя личные работы и локальные prefs. Старые события не воскресают. Delete profile отличается: отзывает сессии и удаляет live-данные; receipt идемпотентен. Offline UI не объявляет облако удалённым. Backup retention/срок удаления утверждаются в эксплуатационном пакете до реальных пользователей.

**CLOUD-08. Ограничения.** Исходные лимиты: 64 операции/512 KiB batch, snapshot до 16 KiB, live-профиль до 64 MiB, 1 000 личных работ. Лимит виден заранее; записи не удаляются молча. Не синхронизировать device prefs звука/движения так, чтобы другое устройство включило эффект. Токены и raw saves не логируются. Личный прогресс не объявляется античит-системой для денежных призов.

## 12. Реклама и платформенное поведение

**ADS-01.** Весь основной функционал бесплатен по progression-правилам. Заработанное не требует просмотра рекламы; нет watermark paywall. Стартовая модель — адаптивный баннер и interstitial на осознанном переходе после нового official completion. Exact ad policy хранится с версией; изменения не меняют RNG/сложность/награды.

**ADS-02.** Первые пять уникальных official completions защищены. Banner скрыт в редакторе, личной тестовой партии, помощи, export preview, диалогах, login/reset/recovery, fullscreen/background. На игре появляется только при подтверждённой геометрии; реальная высота резервируется до attach. На переходе между совместимыми сценами не пересоздавать баннер без необходимости; ни мигание, ни сдвиг «Дальше» под пальцем не допускаются. В защищённых состояниях скрытие обязательно.

**ADS-03.** Interstitial: новый campaign/daily result durably сохранён; отдельное «Дальше»; пройдена защита первых пяти; ≥180 s активной игры после запуска и предыдущего request; ≥3 новых unique official completions после предыдущего request; foreground/SDK readiness; нет открытия главы/полной страницы/export unlock или другого блокирующего слоя. Повторы, помощь, restart, Back и редактор не opportunities.

**ADS-04.** Eligibility расходуется на request, не impression; маркер сохраняется до show. No-fill/error не даёт немедленный повтор. Не готовый SDK → переход без request. Один transitionId/showSessionId, один resume. Фактический показ останавливает ввод/звук до достоверного закрытия; watchdog не возобновляет игру под неизвестным/открытым fullscreen. Background blocker независим от ad blocker.

**ADS-05.** Android Mobile Ads и Yandex Games SDK — отдельные адаптеры. В web проверить API-управление sticky в консоли, иначе стартовый показ нарушит защиту. Test/live конфигурации разделены. Отсутствие рекламы не блокирует core/save/daily. Unit IDs, договоры и paid impressions в этой спецификации не считаются настроенными.

## 13. Нефункциональные требования и измерение

**NFR-01. Производительность.** Цель: непосредственный ввод и устойчивый кадр на заранее зафиксированном минимальном реальном Android-устройстве; имя/ОС/WebView фиксируются в M0. Начальные бюджеты для проверки: 60 Hz gameplay, p95 frame ≤20 ms на целевом среднем устройстве, p95 input-to-visible ≤100 ms, отсутствие повторяющихся >100 ms stalls при drag. На минимальном устройстве допускается согласованный 30 Hz профиль, если прямой ввод и читаемость сохранены. Это acceptance-цели, не текущие измерения.

**NFR-02. Бюджеты.** До массового арта замерить cold start, первые пять задач, 15 минут игры, память/GPU, background/resume и крупный альбом. Начальная цель тёплого локального старта ≤1 s и холодного local playable ≤3 s на указанном устройстве; для hosted web отдельно измерять загрузку ресурсов и сеть. Если не достигнуто, исправить bottleneck либо явно согласовать новый бюджет; не писать PASS по среднему desktop FPS. Первая игра не ждёт всех миниатюр/SDK/сети.

**NFR-03. Надёжность и приватность.** Ни одного потерянного подтверждённого хода/earned права в обязательных fault-сценариях, ни одного двойного completion после replay/callback. Логи не содержат токены, email, имена личных работ, полные board/save. На сервере лимиты размера/rate, resource-level authorization и проверка типов. Не загружать произвольные URL из пользовательского draft.

**NFR-04. Наблюдаемость.** Минимальные события: session/first_input, puzzle_start/resume, accepted_move, help, completion/replay, chapter/reward unlock, daily fetch/entry, draft commit/author completion, export success/cancel, save failure/recovery, sync/conflict/reset, ad opportunity/request/show/dismissal. Игровые факты отправляются после commit со стабильным eventId; telemetry не блокирует игру. Подписи/контент работ и raw proof исключены. Провайдер, хранение и согласия — эксплуатационный выбор до выпуска.

**NFR-05. Продуктовые измерения.** Смотреть прохождение первых пяти, выходы на конкретных задачах, время до следующего осмысленного действия, использование помощи/архива/редактора, повторное создание работ, возвраты D1/D7 и падение продолжений после рекламы. Архивные решения не считать днями удержания. Маленькая выборка/бот/CI не доказывают интерес и коммерческую эффективность; не вводить скрытый директор или ухудшение палитры ради ad opportunities.

## 14. Разрешённые расхождения с прежними материалами

| Прежняя формулировка/артефакт | Актуальное правило |
| --- | --- |
| Прототип только на 15 задач, линейное открытие всех | Релиз 60 + daily; после первых пяти выбор свободнее по §4 |
| A/B/C и «Цветовая мастерская» | Отклонены; направление и референс из §8 |
| Bitmap как обязательный шрифт | Не принят; реальная гарнитура выбирается на одинаковых экранах |
| Тусклая плоская атмосфера браузерной пробы | Только техническое доказательство отклика; целевой характер — приложенная картинка |
| Маленькая квадратная доска/предел 72 px | Полноразмерная сетка, независимые стороны клеток, §9 |
| Победа только в панели вне постоянно видимого поля | Сохранённое поле → цельный фон/призма с доступным возвратом и действиями |
| «Посмотреть финал» без помощи | Только демонстрационная проба; в релизе решение раскрывается по CORE-06 |
| LocalStorage из пробы | Не production storage; TECH-03/04 обязательны |
| Готовые кандидаты/модели = принятая игра | Данные и ограниченные проверки; релиз проходит всю матрицу |

## 15. Открытые решения и условия выпуска

| Gate | Когда закрыть | Ответственный результат |

Эти gates не блокируют написание доменного ядра и документов, но не разрешают объявить соответствующий блок готовым. Не требовать от владельца всех ответов до подготовки конкретного проверяемого варианта. Договоры/платежи/публичная store-публикация — отдельное явное действие владельца.

## 16. Готовность и следующий шаг

Релиз принимается, когда все требования в матрице имеют PASS с build/device/evidence, нет открытых критических дефектов потери данных/доступа/блокировки игры, пройдены оба платформенных адаптера, принят официальный контент и задействован daily-процесс. Невыполненный обязательный блок не маскируется флагом «потом». У каждого milestone есть полезная промежуточная сборка, но она подписана своим объёмом.

Непосредственная следующая разработческая задача — **M0: инициализация consumer и ранняя проверка внешних зависимостей**, затем M1: настоящее ядро с надёжной локальной записью. Художественный срез M2 строится поверх него; массовое оформление выполняется после принятия одного игрового эпизода и победы. В текущем поручении выполняется только спецификация.
