# ХУЕ: монетизация без энергии 0.1

**18 ноября 2026. Выбранная исследователем стартовая политика для реализации и проверки.** Не включение рекламы в опубликованную игру, не настройка кабинета и не прогноз дохода. Рабочие цели — Android/RuStore и Яндекс Игры. [Полный обязательный объём](RELEASE_SCOPE.md), [технический контракт](TECHNICAL_SPEC_0_1.md).

## 1. Конкретный вариант

Базовая игра бесплатная: вся опубликованная кампания, daily/архив, редактор, облако, альбом, чистый экспорт и шесть заработанных макетов доступны по уже установленным правилам. Модель заработка — **адаптивный баннер и редкие interstitial на переходе к следующей задаче**. Платной валюты, энергии, подписки, платных подсказок, rewarded и IAP в этой стартовой политике нет.

Это ограниченный выбор по производственной цене и совместимости с текущим ТЗ. Доходность такой конфигурации не измерена; она может оказаться недостаточной и потребовать отдельного коммерческого решения. Отказ от rewarded здесь сохраняет бесплатную помощь ядра и не создаёт искусственную потребность в новой валюте.

Не подменять earned reward: игрок не смотрит рекламу, чтобы получить уже заработанную карточку, сохранить работу, открыть существующий архив или завершить синхронизацию. Экспорт не получает watermark с платным снятием. Полученные макеты остаются доступными после изменения политики.

## 2. Размещения баннера

| Состояние | Видимость | Геометрия/условие |
| --- | --- | --- |
| Первые пять уникальных официальных задач | Скрыт | Защита начала; official = campaign levelId или daily slotId |
| Меню/кампания/архив/альбом после начала | Допустим | Отдельный зарезервированный слот, доступные CTA и safe areas |
| Обычная campaign/daily партия после начала | Допустим | Только если фактически помещается поле с клетками ≥48 CSS px и все основные controls |
| Результат | Допустим уже существующий слот | Не загружать новый формат так, чтобы он сдвинул «Дальше» под пальцем |
| Редактор, личная тестовая партия, помощь, export preview | Скрыт | Не мешает сравнению цветов и созданию работы |
| Диалог, login, reset/delete, save-recovery, fullscreen, background | Скрыт | Native view не остаётся поверх внешнего окна/контролов |
| Loading/no-fill | Нейтральная зарезервированная область | Без контрастного placeholder и внезапного изменения положения доски |

Android: проверить текущий адаптивный формат SDK с ограничением высоты; исходный рабочий ориентир — не более 50 dp по опыту Seeds, **не универсальный SDK default и не обрезка большого creative**. SDK возвращает реальную высоту для измеренной ширины. Применить kit resolveNativeBannerPlacement, обновить DOM reservation, заново измерить и только потом attach. Все native SDK вызовы на main thread.

Yandex Games: platform sticky через SDK, отдельный адаптер. В консоли обязательно включить управление sticky через API: по умолчанию он может показываться уже при запуске и нарушить защиту начала. Не считать его Android Mobile Ads и не встраивать сторонний рекламный SDK поверх web-платформы.

Новый рекламный слот должен быть учтён в [SCREEN_STATE_SPEC](SCREEN_STATE_SPEC_0_1.md): прежний бюджет поля описан без гарантированной рекламной высоты. Сначала reflow/landscape, убрать вторичный текст из занятой области. Если после измерения поле/кнопки не помещаются, баннер **не показывается на этом экране**, и это фиксируется как geometry-unavailable; сцена не уменьшается ниже допустимых hit-area. Это продуктовая защита подтверждённой геометрии, не эвристика «низкий экран — навсегда выключить рекламу».

Без сети/при no-fill основной функционал работает. Повтор загрузки ограничен и не запускается из каждого error callback. SDK refresh не дублируется собственным таймером. Rotation заменяет поколение banner; поздние callbacks старого view не меняют новый. Системный нижний inset имеет одного владельца, не добавляется и footer, и ad slot.

## 3. Interstitial: все условия одновременно

| Условие | Начальная настройка |
| --- | --- |
| Явный пользовательский переход | Нажатие «Дальше» после нового завершения campaign/daily |
| Сохранение | Победа и права уже durably записаны |
| Начало игры | Пять уникальных official завершений; первый возможный запрос — на более позднем незапрещённом переходе |
| Grace после запуска процесса | Не менее 180 секунд активной игры |
| Пауза между запросами | Не менее 180 секунд активной игры после последнего request |
| Новое продвижение | Не менее трёх новых уникальных official завершений с предыдущего request; повторы не считаются |
| Состояние | Foreground, нет другого fullscreen, нет save/login/conflict слоя |
| Особый результат | Не выдаётся открытие главы, полная страница или новый export-layout |
| Готовность адаптера | Android: есть загруженный creative. Yandex Games: SDK/метод готовы; отдельного preload/readiness creative эта поверхность API не обещает. Если адаптер не готов — переход без запроса |

Первый unlock export-caption при пятом завершении защищён отдельно; interstitial на нём не появляется. Новая обычная карточка за решение сама по себе **не** является защищённым milestone, иначе все возможности показа исчезнут. Защищённые milestones не расходуют рекламную возможность — следующий подходящий новый результат может её использовать.

Повторы пройденных задач, рестарт, просмотр решения, выход назад, редактор/авторская проверка, вход в облако, отмена диалога, открытие настроек и запуск приложения не являются interstitial opportunities. Загрузка рекламы никогда сама не вызывает show.

Числа 180 секунд / 3 результата — проектная стартовая конфигурация. Они не взяты как доказанный доходный оптимум из конкурентов. Политика получает adPolicyVersion; изменение не меняет content RNG, сложность, награды или длину самой задачи.

## 4. Время, no-fill и callback-последовательность

Активное время берётся из монотонного foreground gameplay таймера, без рекламы, background и меню. Локальные календарные часы не ускоряют cooldown. При запуске нового процесса даётся новый 180-секундный grace; сохранённый прогресс/пауза не сокращаются. Это консервативная защита от частых показов после relaunch, не обещание глобального рекламного лимита между всеми устройствами.

Eligibility расходуется **при request**, как в ActionInterstitialGate, не только при impression. Записать request marker и обнуление newSinceRequest до вызова show; ошибка записи → перейти без рекламы. No-fill/show-error после request не разрешают немедленный новый запрос. Если SDK ещё не готов и request не начинался, cooldown не расходуется. Повтор eligible route event с тем же transitionId игнорируется.

Порядок:

1. Зафиксировать победу и обычные награды, показать устойчивый результат.
2. Получить отдельное нажатие «Дальше» и пересчитать условия на текущем состоянии.
3. Если любое условие не выполнено — сразу открыть следующую задачу.
4. Если выполнены — записать request marker, остановить конфликтующий ввод и вызвать platform show с уникальным showSessionId.
5. При pre-show error/no-fill — открыть следующую задачу, сохранив request cooldown.
6. При фактическом показе — игра и звук остаются приостановлены до достоверного dismissal. Для отсутствующего **pre-show** callback начальный deadline 10 секунд; timeout не доказывает отмену вызова. Если адаптер доказал завершение без показа, продолжить. Если судьба show неизвестна, показать явное восстановление с сохранённым результатом и возможностью перезапуска клиента; не возобновлять активную новую задачу под неотменённым show. Генерация JS сама по себе не отменяет SDK. В web onClose(wasShown=false) считается завершением без показа, отдельного выдуманного preload API нет.
7. После закрытия снять только ad blocker; background blocker действует независимо. Переход выполняется один раз.

Действительно показанную рекламу нельзя «закрыть» общим watchdog и возобновить игру под ней. Это особенно важно при выборе kit web wrapper: его документированные timeout гарантии должны быть сопоставлены с фактическими SDK-событиями. До доказанной интеграции это остаётся release gate. Для Android runtime recipe уже различает pre-show deadline и фактически открытый fullscreen.

## 5. Платформы и конфигурация

| Цель | Реклама | Что проверить перед выпуском |
| --- | --- | --- |
| Android/RuStore | Yandex Mobile Ads, native bridge | Test/live разделены, отдельные unit IDs, реальные view/callbacks, lifecycle и звук после возврата |
| Яндекс Игры | Yandex Games advertising SDK | Hosted draft, platform-ready/loading/gameplay API, разрешённое размещение sticky/fullscreen и текущие требования |
| Дополнительные площадки | Адаптер после отдельной проверки | Доступность публикации/монетизации/выплат и стоимость адаптации, а не механическое включение чужого SDK |

Проверять наличие конфигурации без вывода значений в логи. Demo IDs и тестовые сборки не являются доказательством оплаченного показа. Release не содержит runtime-переключатель на mock через window global. Опциональный рекламный startup не блокирует Play, local save или daily cache. Никаких операций с кабинетами/договорами/платёжными данными этим исследованием не выполнено.

Точные SDK версии закрепить в consumer lockfile по проверенному Android scaffold и текущему API на момент интеграции. Документ SDK, прочитанный сегодня, не делает старый APK совместимым автоматически.

## 6. Измерение без искусственной сложности

Минимальные события: opportunity, skipped(reason), request, load_success/error, show, impression, dismissal, show_error, route_resume. Сохранённые игровые milestones отправляются после commit с устойчивым eventId. В аналитике не передавать provider tokens, raw save, имена личных работ или полные board данные.

Смотреть отдельно:

- сколько новых задач решают до и после первого объявления;
- сколько eligible opportunities реально дошли до impression;
- долю no-fill и причины geometry-unavailable;
- продолжение следующей задачи после dismissal;
- отказ/выход на защищённых и обычных переходах;
- реальные отчёты рекламного кабинета отдельно от приблизительных SDK events.

Не делать вывод «реклама увеличила доход без потери удержания» из build, тестовой сессии или одного игрока. Если появляются пользователи, сравнивать одинаковые content/version/cohort окна и оценивать сам игровой опыт. При давлении на UX сначала менять размещение/частоту; не ухудшать палитры, не добавлять скрытые штрафы или forced help ради ad opportunities.

## 7. Проверка и статус

В [54 сценариях технической модели](evidence/technical-contract-checks-2026-11-18.json) есть чистые проверки условий user action, durable save, нового official результата, protected milestone/fullscreen/background, grace, ready, request/no-fill и следующего интервала. Они проверяют выбранную policy function, **не исполняют SDK** и не замеряют доход.

Будущая реальная приёмка: два orientation и safe areas; text 150%; первая пятёрка; несколько unlock на одной победе; no-fill; ошибочный native callback; double tap; process restart; background во время fullscreen; callback старого banner; отсутствующий pre-show callback; реальный dismissal; mute и возврат управления. Отдельно — убедиться, что отсутствие рекламы не лишает задачи, помощи, экспорта или облака.

Источники: [Android interstitial](https://ads.yandex.com/helpcenter/en/dev/android/interstitial), [adaptive inline banner](https://ads.yandex.com/helpcenter/en/dev/android/adaptive-inline-banner), [Yandex Games ads](https://yandex.ru/dev/games/doc/ru/sdk/sdk-adv), проверены 18 ноября; точные kit recipes и границы источников — в [реестре](evidence/technical-sources-2026-11-18.json). Источники подтверждают интеграционные правила, не наши cadence числа.
