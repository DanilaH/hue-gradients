# ХУЕ: технический контракт 0.1 — сохранение, identity, cloud, daily

**18 ноября 2026. Рабочий вариант для разработки.** Обязательные функции из [RELEASE_SCOPE](RELEASE_SCOPE.md) сохранены: без энергии, с метой, daily, редактором и облаком в первом релизе. Конкретный стек и лимиты ниже — выбранное исследователем решение; инфраструктура не заказана, аккаунты/секреты не созданы, приложение и production API не развёрнуты.

## 1. Решение и границы

Рабочие целевые сборки: **Android/RuStore и Яндекс Игры**, с общим TypeScript ядром и раздельными платформенными адаптерами. Это план реализации для известных рабочих каналов; остальные доступные площадки не отсекаются и добавляются после проверки их требований. Синхронизация нескольких устройств одного подтверждённого профиля обязательна. Автоматическое объединение аккаунтов разных платформ по имени/email не выполняется.

Для web взять проверенный Phaser/Vite bootstrap из mini-games-kit **4e826ff378dfd2f4705a31a894400ae6268ca6f9**. У него зафиксированы Phaser 4.2.1, TypeScript 7.0.2, Vite 8.2.2; это прочитанный package manifest, не рекомендация незаметно обновить существующие игры. Новый consumer хранит runtime pin и guidance pin отдельно. Android использует тот же игровой модуль в Capacitor, но native lifecycle, SQLite и рекламный адаптер принимаются отдельно: полноценного проверенного Android bootstrap в kit нет.

Облако — **собственный небольшой HTTPS API на TypeScript/Node и PostgreSQL**. Одна служба, одна база, без брокера сообщений и универсальной игровой платформы. Daily — публичный endpoint того же сервиса и статические versioned JSON; вход для получения задач не нужен. Выбранное место эксплуатации — инфраструктура под контролем владельца в РФ; конкретный хост, домен, договор и резервирование требуют настройки перед запуском. Размещение само по себе не доказывает выполнение требований к данным.

Почему не один platform save: в kit YandexMirroredStorageAdapter даёт best-effort mirror, не арбитраж двух устройств; у platform Player Data ограничение объёма, а fulfilled setData с flush=false ещё не означает доставку. Список работ и сохранённых версий будет расти. Выбранный сервер обеспечивает атомарные операции, изоляцию профилей, epoch и графы версий. Цена — отдельный backend и его сопровождение; обязательное cloud нельзя объявить готовым из-за наличия метода write().

## 3. Локальное хранилище и подтверждение записи

Android: ограниченный native bridge к SQLite; web: IndexedDB. Оба реализуют один потребительский интерфейс commit/load/readOperation, но их физические гарантии и lifecycle тестируются раздельно. Web storage может быть очищено браузером; локальное «Сохранено» не равно сохранённой серверной копии. SDK safeStorage использовать для небольших platform metadata, если требуется SDK; не подменять им большую транзакционную базу.

В одной транзакции записать:

- следующий snapshot попытки/черновика;
- завершение и производные права, если возникли;
- operationId и результат команды;
- неизменную запись outbox для аккаунта, либо локальный гостевой факт для последующего переноса.

Только после успешного COMMIT сообщить «Сохранено на устройстве» и подтвердить награду. Запись отдельного поля, затем награды, затем outbox без общей транзакции запрещена. Визуальный эффект не является подтверждением; optional analytics/ads/cloud не стоят на пути локального старта.

Один writer на профиль. Native DB сериализует операции, браузерные вкладки используют transactional compare-and-set по localRevision внутри IndexedDB, а не только Promise очередь/BroadcastChannel. При конфликте перечитать состояние и пересчитать действие; старый готовый snapshot с новым номером не становится актуальным. Транзакция IndexedDB должна содержать только её DB-запросы, без ожидаемого сетевого вызова.

Каждый commit получает UUID operationId **до** первой попытки записи. Если результат неизвестен, закрыть только изменяющие save действия, прочитать operation ledger и авторитетное состояние. Найдено применение → вернуть подтверждённое состояние; доказано отсутствие → повторить тот же operationId; прочитать не удалось → recovery UI. Не пересоздавать награду из старого in-memory объекта.

Запись после обмена должна сохранять board, moves и assisted вместе. Просмотр помощи сначала сохраняет assisted=true. Новая попытка имеет новый attemptId; replay прежнего старта не создаёт ещё одну base completion. Не держать весь ввод за сетевой синхронизацией.

## 4. Сущности и идентичность

| Сущность | Ключ / важные поля | Инвариант |
| --- | --- | --- |
| Profile | server profileId; progressEpoch; workspaceRevision | Владелец определяется проверенной сессией, не присланным profileId |
| Device | случайный installationId + подтверждённая регистрация у профиля | Не рекламный/device hardware ID; переустановка создаёт новый ID |
| Operation | profileId + epoch + operationId; type; immutable payloadHash | Повтор тех же байтов применён однажды; тот же ID с другими данными — 409 |
| Completion | profile + epoch + source + logicalId | Campaign levelId или daily slotId; revision не создаёт вторую карточку |
| Best | profile + epoch + fingerprint + rulesVersion + assistanceCategory | Минимум только среди сопоставимых результатов; помощь отдельно |
| Attempt | attemptId; content ref/hash; nodeId; parentNodeIds; board; moves; assisted | Snapshot неизменен, assist не сбрасывается внутри попытки |
| Work | draftId; provenance; revision graph; selectedHead | Копия исходника — личная работа с отдельным ID |
| Work revision | nodeId; parentNodeIds; fingerprint; data; metadata | Конфликтующие ветки сохраняются обе; имя не меняет gameplay fingerprint |
| Earned right | profile + epoch + rewardId | Производное от уникальных фактов, не клиентское increment(1) |
| Outbox | operationId; destination profile/epoch; payload; retry state | Адресат фиксируется до отправки; смена аккаунта не перенаправляет событие |
| Content | logicalId; contentVersion; rulesVersion; SHA-256 snapshot | Опубликованный файл неизменен |
| Daily slot | UTC YYYY-MM-DD + active revision ref/status | Счётчик награды привязан к слоту, не revision/дате доставки |

Результат содержит подтверждённый snapshot/attempt chain и категорию помощи. Server валидирует структуру, принадлежность, content/rules ref, допустимую перестановку, итог и базовые счётчики; malformed результат не засчитывается. От модифицированного клиента с полностью сфабрикованной личной историей этот контракт не обещает античит. Денежных призов/рейтингов нет; добавление таких стимулов потребует иной модели доверия.

## 5. Identity и сессии

**Android:** добровольный вход через Яндекс ID, authorization code + PKCE S256 и state в системном браузере/проверенном native flow. В приложении нет client_secret. Redirect URI регистрируется точно; для Android выбрать проверенную app link привязку домена и пакета/сертификата. Code/state и одноразовый verifier имеют ограниченную жизнь и не пишутся в аналитические события.

Полученный OAuth token передать нашему backend по HTTPS для обмена на собственную сессию. Backend сам запрашивает user info, проверяет ожидаемый client_id и получает идентификатор; присланные клиентом uid/email/name не являются доказательством. Identity key — provider + client_id + psuid; внешние ID не равны внутреннему profileId. Запрашивается минимальный доступ к идентификатору, без email/avatar/контактов; точный разрешённый набор проверяется в зарегистрированном OAuth-приложении. Provider token после проверки не хранится как игровой refresh token.

**Яндекс Игры:** вход только осознанным действием через платформенный SDK; стороннюю форму регистрации не показывать. Подтверждение на нашем сервере — signed Player data с проверкой подписи секретом игры по документации, не голый getUniqueID(). Identity namespace отдельный: platform + appId + verified playerId. Нельзя предполагать равенство Android psuid и ID игрока.

**Обнаруженная зависимость:** официальный Player SDK указывает получение секретного ключа после подключения инап-покупок. Наличие такого ключа для нашей ещё не созданной игры **не проверено**. До реализации разработчик должен подтвердить console capability и провести реальный signed-player exchange; без неё web cloud не проходит приёмку. Не ослаблять проверку до доверия userId. Подключение технической возможности подписи не означает, что магазину автоматически добавлен платный товар.

Сессии нашего API: непрозрачный случайный access token, срок 15 минут; только hash серверного секрета в БД. На Android — rotating refresh family с 30 днями неактивности и максимумом 90 дней, токен под защитой native storage/Keystore. Один refresh in-flight; одна повторная отправка исходного запроса после обновления. Потеря ответа refresh допускает повтор того же refreshRequestId в коротком окне 60 секунд: сервер хранит зашифрованный результат для этой операции; другой запрос со старым использованным токеном отзывает family. Эти сроки — выбранная конфигурация, не ограничения Яндекса.

В web access token держится в памяти, повторная сессия создаётся через действующее platform proof; долгоживущий refresh в localStorage не нужен. Подпись/токен не логируются; timestamp и формат proof проверяются по фактическому контракту SDK, воспроизведение вне его freshness window отклоняется. Конкретный verifier обязан иметь тесты на неверный app/key/algorithm/формат/срок — модель из этого пакета **не исполняет cryptographic auth**.

Logout локально закрывает доступ к account vault, прекращает его worker и очищает токены; необработанные события остаются у исходного аккаунта. Если сеть недоступна, UI не говорит «Сессии отозваны на сервере». Logout-all/revoke требует подтверждённого ответа. Вход не появляется сам при запуске, no-fill или завершении задачи.

## 6. Перенос гостя и переключение аккаунта

1. Остановить новые записи источника и завершить принятые операции. Сохранить подтверждённый guest snapshot и transferId.
2. Подтвердить целевой аккаунт, загрузить server epoch. Показать объединение количества работ/результатов и найденные конфликты.
3. Отправить перенос chunk-ами с неизменными source IDs, transferId и destination. Перезапуск/повтор использует те же ключи; epoch проверяется для каждого chunk.
4. Завершить transfer receipt только после всех chunk. Если reset случился между ними, старый перенос не завершается, остаток сохраняется локально.
5. После подтверждения сохранить account vault и consumed-to marker гостевого источника одной локальной транзакцией. Только затем активировать новый пустой guest vault. Исходная резервная копия доступна для восстановления до успешного контрольного чтения.
6. Не переносить уже consumed guest автоматически в другой аккаунт. Account A → guest → account B не получает копию A.

Данные профилей изолированы по ключам даже в одном DB-файле. Сетевой callback с устаревшим sessionGeneration может завершить операцию только своего адресата и не переключает текущий UI. Уход из аккаунта с зависшим cloud не обязан ждать сеть бесконечно: локальный writer закрывается, outbox остаётся связан с прежним владельцем.

## 7. Протокол синхронизации

Ручки имеют префикс /v1. Тела — UTF-8 JSON, неизвестные поля не принимаются молча в изменяющих командах. Лимиты начальной конфигурации: 64 операции и 512 KiB на batch, отдельный пользовательский snapshot до 16 KiB, совокупное live-состояние профиля до 64 MiB, не более 1 000 личных работ. Лимит сначала показывается пользователю; сервер не удаляет старые работы, чтобы вместить новую. Значения меняются версионированной политикой и не превращают старые сохранения в битые.

| Метод / путь | Вход | Ответ и поведение |
| --- | --- | --- |
| POST /sessions/yandex-id | OAuth proof, installationId | Проверенная сессия, profileId, epoch, serverNow; без доверия клиентскому UID |
| POST /sessions/yandex-games | signed Player proof, installationId | Сессия отдельного platform namespace; неверная подпись — 401 |
| POST /sessions/refresh | refreshToken, refreshRequestId | Одна rotation или идемпотентный повтор Android |
| DELETE /sessions/current | access session | Отзыв текущей сессии; локальный logout возможен независимо |
| GET /sync?cursor=…&limit=… | opaque cursor, максимум 256 записей | Последовательные изменения и highWatermark; cursor принадлежит профилю/epoch |
| POST /sync/operations | epoch, operations[{id,type,payloadHash,payload}] | Весь batch атомарно; receipts applied/already-applied, serverRevision и cursor |
| GET /operations/{id}?epoch=… | прежний id | Статус применения; разрешает неизвестный сетевой ответ |
| POST /profile/reset | expectedEpoch, operationId, recentAuth | Новый epoch, идемпотентный reset receipt |
| DELETE /profile | operationId, recentAuth, явное подтверждение | Отзыв сессий и deletion receipt; повтор безопасен |
| GET /daily?month=YYYY-MM | публично, без профиля | serverNow, catalogVersion, published slots, ETag; будущего содержимого нет |
| GET /content/{sha256}.json | immutable ref | Точные байты уровня; immutable cache |
| GET /health | без пользовательских данных | Доступность; не требуется для запуска офлайн-игры |

Server извлекает владельца из сессии. Все запросы сущностей ограничены owner/epoch; чужой draftId, cursor или operationId не раскрывает чужие данные. Нельзя включить произвольный profileId в JSON и выполнить запрос от его имени.

Operation hash вычисляет сам сервер по нормализованным id/type/payload; присланный payloadHash только сверяется. Для схемы 1 числа целые safe integers, ключи определены ASCII-схемой, повторяющиеся JSON-ключи отвергаются. Canonical serialization: ключи лексикографически, без пробелов, UTF-8, строки без Unicode normalization, только обязательное JSON escaping. Другая запись тех же нормализованных данных не создаёт новый эффект. Клиентские wall-clock timestamps не участвуют в выборе победителя и не заменяют operationId.

В PostgreSQL каждый изменяющий batch берёт блокировку строки profile FOR UPDATE и проверяет epoch **в той же транзакции**. Unique constraints защищают operationId, completion и rewardId; result и ledger пишутся вместе. Reset использует ту же блокировку. При потере ответа клиент повторяет тот же batch/IDs; двойное исполнение не даёт второй награды. Opaque cursor/highWatermark обеспечивают неизменную границу страницы; новая запись не заставляет пропустить старую.

Ошибки: 400 malformed; 401 повторить auth один раз; 403/404 чужой ресурс; 409 EPOCH_MISMATCH / OP_ID_REUSED / MISSING_PARENT / UNSUPPORTED_REVISION; 413 размер; 422 недопустимый snapshot; 429 Retry-After; 5xx/timeouts временные. При неизвестном результате POST не создавать новые IDs. Отказ отдельной операции откатывает batch целиком. Уже применённые повторы внутри корректного batch дают already-applied. Event receipts и реальные domain objects проверяются до объявления sync complete.

Локальный sync worker: один запрос push на профиль; batch при победе/выходе из редактора и в foreground не чаще одного раза в 10 секунд. Задержка не отменяет queued факты. Retry с jitter и базой 2/5/15/60/300 секунд, учитывать Retry-After; 401/409 не крутить бесконечно. Timeout ожидания 10 секунд не означает отмену серверной операции; повтор безопасен по ID. Фоновая ОС не обязана разрешать отправку; гарантируем сохранённую очередь, а не доставку за N секунд после закрытия.

При исчерпании outbox/storage нет молчаливого discard. Уже сохранённая игра доступна; новая запись показывает недостаток места и восстановление/синхронизацию. Очистка кеша контента не удаляет рабочие черновики, несинхронизированные операции или две конфликтующие ветки.

## 8. Слияние и конфликт

Завершения объединяются по logical keys; best — minimum в своей категории; заработанные права не отнимаются после повышения порога. Server пересчитывает права из уникальных фактов и policyVersion, не принимает клиентское «добавить ещё один формат».

Попытки и работы имеют неизменные node IDs и parent links. Если A — предок B, активен B; если у A и B общий предок, но они не предки друг друга, обе вершины сохраняются. Выбор пользователя создаёт resolution node с обеими вершинами как parents и выбранным snapshot; старые ветки остаются восстановимыми. Счётчик ходов и wall-clock не определяют победителя конфликта. Parent из другой работы/профиля отвергается; неизвестный parent нужно дослать либо явно создать recoverable branch, не уничтожая текущую.

assisted внутри одной attempt lineage монотонен: новый snapshot не может сменить true на false. При явном объединении состояния из assisted и clean веток не переносить clean best на assisted историю; лучший результат относится к конкретной завершённой ветке. Авторское прохождение сохраняется по fingerprint + rulesVersion, rename не снимает его.

Настройки устройства (звук, haptics, reduced motion) локальны: чужой телефон не включает звук. Это уточняет неопределённую ранее приоритетность настроек в 0.2. Облачные настройки профиля (имя, выбранная текущая работа) меняются compare-and-set по entity revision; конфликт отображается без потери данных. Отсутствующее поле при старой schema не сбрасывает новое.

Полная история editor revision не чистится молча. Сжатие attempt history допускается только после сохранения необходимых ancestor IDs и текущих/конфликтующих snapshot; неизвестный старый checkpoint после долгого офлайна принимается через явное восстановление отдельной ветки. До такой реализованной процедуры ничего не «оптимизировать» удалением случайных последних N IDs.

## 9. Reset, удаление и миграции

Reset прогресса — online, recent auth (не старше 5 минут), понятное подтверждение. Он очищает campaign/daily/earned progression/attempts, увеличивает progressEpoch, сохраняет личные работы и локальные настройки. Старые outbox события не переписываются автоматически в новую epoch; UI предлагает отдельно восстановить собственные незавершённые работы. Старые completed-факты отвергаются.

Reset operation ledger находится вне сбрасываемого пространства: повтор после потерянного ответа возвращает ту же новую epoch, а не делает второй reset. Транзакционная блокировка исключает гонку «reset проверен, затем старая запись применилась».

Delete profile отличается от reset: закрыть сессии, удалить профиль и содержимое из live-хранилища, выдать receipt; старый auth не может воскресить профиль. Переход на удалённый профиль локально изолирует его кеш/очередь и предлагает сохранить личную копию работ отдельно от облачного аккаунта. Политику удаления резервных копий, сроки и уведомление пользователя согласовать в эксплуатационном/privacy пакете до реальных пользователей; не обещать мгновенное физическое исчезновение всех backup.

Миграции локальной schema и серверной schema версионируются отдельно от content/rules/policy. Перед destructive migration сохранить recoverable backup; validate→migrate→validate→commit. Старая сборка при неизвестной schema открывает recovery/обновление, не пишет пустые defaults. Изменение fingerprint/rules не переносит best без доказанной совместимости; уже полученная базовая карточка не размножается.

## 10. Daily manifest и кеш

Пример публичного envelope:

```json
{
  "schemaVersion": 1,
  "catalogVersion": "example-only-v1",
  "serverNow": "2026-11-18T12:00:00Z",
  "slots": [{
    "slotId": "2026-11-18",
    "status": "published",
    "contentId": "gradient-daily-001",
    "contentVersion": "example-only-v1",
    "rulesVersion": "gradient-rules-1",
    "sha256": "<64 hex characters>"
  }]
}
```

Это пример формата, **не публикация нашего кандидата на указанную дату**. Банк 30 daily по-прежнему UNASSIGNED. Server выдаёт только реально опубликованные UTC-слоты не позже текущего дня. Endpoint доступен гостю. Пользовательские даты устройства не являются основанием публикации.

Download → проверить HTTP/лимит/JSON/schema → SHA-256 точных байтов → contentId/version/rules/поле → атомарно установить ref+blob в кеш. Если скачивание оборвалось, hash не сошёлся или identity не совпала, старый пригодный кеш остаётся. Hash защищает целостность, а источник доверия — собственный HTTPS origin; произвольный URL из работы редактора не загружается сервером.

После новой даты уже загруженный snapshot старой попытки остаётся прежним. Archived slots засчитываются один раз. Если задача ошибочна, catalog хранит статус withdrawn и явную замену revision; новый запуск использует допустимую revision, старое завершение/earned сохраняется. Незавершённую отозванную задачу нельзя тихо заменить внутри поля: предложить новую попытку; сохранить старую локальную копию для восстановления без повторной награды.

Offline можно играть в полученные ранее published snapshots. Новая задача требует актуального опубликованного каталога; перевод часов не открывает будущую. Кеш с устаревшим serverNow показывает последнюю проверенную дату, не притворяется сегодняшним live-состоянием. Отсутствие нового слота ведёт в архив, не к автогенерации непроверенного уровня.

Publisher workflow: принять задачи → загрузить immutable blobs → проверить доступность/hash → одной DB-транзакцией назначить slots и новый catalogVersion → наблюдать endpoint. Не публиковать manifest раньше его blobs. Архив постраничный по месяцам, не раздувающийся единственный JSON. Начальный редакционный запас и человеческая проверка описаны в контентном ТЗ.

## 11. Что реально исполнено

[check_technical_contracts.py](tools/check_technical_contracts.py) → [54 результата](evidence/technical-contract-checks-2026-11-18.json). Python standard library, SQLite 3.53.1 на этой среде:

- уникальные completions, разделение best, повтор одного operationId и отказ при изменении payload;
- откат всего batch при ошибке второй операции; изоляция profile A/B в handler модели;
- два SQLite connection с параллельными записями;
- неизменные draft nodes, две расходящиеся ветки и явное разрешение;
- reset receipt, epoch и отложенная старая операция;
- **два фактических завершения дочернего процесса**: после эффекта до COMMIT и после COMMIT до ответа; восстановление и повтор;
- UTC/граница суток/leap day, исключение будущего/withdrawn, hash/identity кеша;
- выбранные рекламные gates.

Модель принимает уже проверенный principal и синтетические результаты. Она не проверяет OAuth, весь игровой reducer, authority реального SDK, PostgreSQL, IndexedDB/native SQLite bridge, HTTP, устройство или retention. Два SQLite connection не доказывают production PostgreSQL concurrency. Пройденная логика не является готовым облаком.

Воспроизведение из каталога исследования:

## 12. Порядок реализации и обязательные критерии

1. Создать consumer из точного bootstrap, закрепить инструкции, реализовать ядро и две local storage реализации. Реальные process death/upgrade/две вкладки — до cloud.
2. Сделать API и PostgreSQL схему; адаптировать fixtures к настоящим запросам и транзакциям; проверить чужие resource IDs, reset race, unknown response и cursor.
3. Подключить оба identity flow, секреты/redirect/signatures и реальные два устройства. Наличие signed-player ключа — gate web cloud, не повод ослабить auth.
4. Реализовать guest transfer, revision conflicts, outbox, квоты, delete/reset/migrations; проверить сетевые отказы и смену аккаунта.
5. Поднять публичный daily catalog, publisher и monitor; только после человеческой приёмки назначить даты.
6. Применить [рекламную политику](MONETIZATION_SPEC_0_1.md), UI/cloud-состояния и физические проверки.

Перед production обязательны: рабочие backup и restore rehearsal; исключение токенов/сырых save из логов; ограничения body/rate/owner; мониторинг ошибок записи, age outbox, несоответствий manifest и запаса daily; реальная privacy/account-delete процедура. Домен, хост и registered app identities — эксплуатационные значения, которые ещё не существуют, а не недописанные игровые правила.

Следующая независимая часть полного handoff — художественный профиль/ключевые экраны и проверка контента людьми. Все исполняемые платформенные и серверные проверки остаются у реализации.
